All notable user-visible changes to Vibecodium. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow the VSCodium scheme `<vscode-version>.<build>` plus a Vibecodium revision once releases start.

## [Unreleased]

### Added

- The pinned nightly runtime is now held to two enforced intake gates instead of a documented review. The manifest loader requires every remote archive URL in `vibe/sidecars.json` to be exactly `https://github.com/<source>/releases/download/<version>/<file>.zip` with a plain `.zip` asset name, so a rewritten manifest can no longer keep the pinned digests and point the installer at another repository (a loopback `http` pin stays the local test seam and is exempt). `assertIntakePolicy`, `installSidecar` and a new `node vibe/tools/sidecar-intake.mjs` step in `verify` refuse a pin that has not been public for seven days as `intake-too-recent`, and a pin dated in the future fails closed the same way, so a re-pin without a review no longer depends on the radar row alone; the CLI accepts `--now YYYY-MM-DD` to replay a recorded date. The installer refuses a too-recent pin before any fetch or write, offline verification of an already installed runtime is unaffected, and a signed/authenticated manifest would close the remaining swapped-manifest risk.
- The pinned local runtime can now install into a directory the application owns instead of only a caller-supplied path. `src/stable/runtime/app-data.mjs` resolves the platform application data root (`%LOCALAPPDATA%\Vibecodium` with `%APPDATA%` as the fallback, `$XDG_DATA_HOME/vibecodium` or `~/.local/share/vibecodium`, and `~/Library/Application Support/Vibecodium`) from own data descriptors, and derives one runtime directory per pin, `<root>/runtime/<platformKey>/<id>-<version>`, then proves it stays strictly inside the canonical root after symlinks and junctions are resolved. `installSidecar` and `verifySidecarInstall` accept `ownedRoot` as an alternative to `targetDir`, refuse both together or neither, and map an unownable root or a junction escape to `invalid-destination` without echoing the path; the first-run wizard's `sidecar` bag accepts `appDataRoot`, the verifier receives exactly `{ ownedRoot, platformKey }` and the installer the same bag plus its existing `signal` and `onProgress` controls, so the installer derives the directory itself and no caller-supplied install path reaches a write. The legacy `targetDir` and the `<destinationDir>/runtime` default remain for a host that already owns a runtime, and the host wiring that supplies the root is M6/M12. One live install/start smoke on a clean Windows machine and the authenticated-manifest gate remain M3/M12 work.
- The host can now start the local runtime and get a ready provider client in one call. `createLocalProvider({ wizard, policy })` in `src/stable/runtime/local-provider.mjs` reads the first-run start plan, starts the delivered `llama-server` supervisor (or adopts a selected Ollama daemon), reads the controller's API key through `auth()` and hands a ready B1 `llama-cpp` (or `ollama`) client to the host, so the local chat path now authenticates against the supervisor while the key stays in the supervisor and the client closure. The pinned start plan now carries the catalog chat entry's `id` as the B1 model name, so the host no longer maps the installed weights file back to a provider model. A blocked wizard, a malformed hand-off, a throwing wizard and a supervisor failure are reported as bounded codes that carry no key, path, URL or injected message; a stop during a start ends `stopped` with no failure and a later start reuses the same runtime and key, `dispose()` refuses a later start, and `status()`/`describe()` are key-free. The live loopback smoke with the pinned `b12426` binary and the packaged catalog copy remain open.
- The local runtime now starts `llama-server` behind an API key that the controller owns for its lifetime. The supervisor generates a 43-character `base64url` key, hands it to the child only as `LLAMA_API_KEY` in the allowlisted environment (written last, with case-variant names removed on Windows), and adds `--no-webui` and `--cors-origins localhost` to the fixed flag list, so the embedded web UI is off and a page in a local browser cannot drive the model while the key keeps another local process out. `createLlamaServer` accepts an optional caller `apiKey` (32 to 128 printable ASCII characters, no comma, quote, backslash or whitespace, because llama.cpp parses the value as a CSV key list, and no control, format or bidi character), rejects anything else as a bounded `invalid-api-key` error that never echoes the value, no longer lets `commandArgs` set `-m`, `--api-key`, `--api-key-file`, `--model`, the UI flags, the CORS flags or `--allow-unauthenticated-tools` (an `=` spelling is refused too, and so is the underscore spelling llama.cpp rewrites to a hyphen), refuses the remote-model sources `-mu`/`--model-url`, `-hf`/`--hf-repo` and `-dr`/`--docker-repo` plus the peer tunnel `--connect`, and refuses an `env` override of `LLAMA_API_KEY`. Readiness is now two probes: `/health` must answer 200 and an authenticated `/props` request must answer 200 with the key, so a listener that answers the public health endpoint but rejects the key fails `readiness-mismatch` and the child is reaped (a listener that answers 200 on both endpoints is still accepted, which stays a recorded port race), and `health()` reports the authenticated answer. The key is exposed only through a frozen `auth()` accessor on the controller, is reused across a stop and restart, and appears in no status, snapshot, argument list, error or retained child-output tail. Because the runtime now rejects unauthenticated requests, the B1 `llama-cpp` preset moves from `auth: 'none'` to `auth: 'bearer'` (still `apiKeyRequired: false`, so an unkeyed plain server keeps working), so a client that receives the key sends it. Handing `runtime.auth().apiKey` to that client is delivered by `src/stable/runtime/local-provider.mjs` (see the entry above); a live install/start smoke, bundling and M12 packaging remain open.
- First-run setup now carries a separate embedding start plan for the delivered embedding weights. `embeddingPlan()` reports the pinned executable and the embedding model's file with the recorded `--embedding --pooling last -ub 8192` flags and the same bounded restart policy as the chat plan, or, when a discovered Ollama daemon is the selected runtime, its loopback base URL and embedding model; a daemon with only a chat model, a missing runtime or a wizard that is not ready yields a bounded reason instead. `embeddingRuntimeOptions()` returns exactly the `createLlamaServer` fields (`executablePath`, `modelPath`, `commandArgs`, `restart`), frozen at both levels, so the caller hands the plan to the supervisor without rebuilding flags and the supervisor re-validates every argument. The setup panel gains an escaped **Embedding server** section that shows the plan or its blocked reason; the wizard still never spawns a process, so wiring the index to the embedding server remains M6 work. The llama.cpp binary bundle and the packaged catalog copy remain M3/M12 work.
- The pinned local runtime and models now carry a checked third-party notice. `vibe/licenses/` holds the verbatim MIT, Apache-2.0 and Apache-2.0 WITH LLVM-exception texts (the LLVM/OpenMP text is the exact `LICENSE-LLVM-OpenMP` from the pinned archive), `vibe/notices.json` pins each text by SHA-256 and upstream URL, and `src/stable/runtime/third-party-notices.mjs` projects the shipped sidecar and model pins into frozen components and renders one deterministic notice document. `node vibe/tools/notices.mjs --write` regenerates `docs/vibe/legal/THIRD-PARTY-NOTICES.md`, and `node vibe/tools/verify.mjs` now runs the notices check as its own step: a pinned component whose license has no notice text, a text whose digest drifted from the ledger, or a stale checked-in document fails the build. Placing the notice beside the installed application and the Microsoft VC++ runtime notice remain M12 packaging work.
- The local runtime now has a pinned `llama-server` installer. `vibe/sidecars.json` pins the llama.cpp nightly Windows x64 CPU archive (`b12426`, MIT plus the Apache-2.0 WITH LLVM-exception OpenMP runtime, published 2026-11-15) by exact byte size and SHA-256, and `src/stable/runtime/sidecar.mjs` installs it without a bundler or a dependency: a credential-free bounded transfer verifies the archive, a pointer-free ZIP reader accepts only the 23 allowlisted runtime files, a final redirect to a literal loopback, private, link-local or metadata host (including the IPv6 forms that embed an internal IPv4 address and the `fe80::/10`, `fc00::/7` and `ff00::/8` ranges) is refused when the pin was not loopback, a nested parent must resolve inside the target directory, and every extracted file is checked against its own pinned size and digest before a per-file atomic install. Only names that exactly match the pin are written, so a zip-slip, absolute, drive-letter, backslash or symlink entry cannot leave the target directory, and every file is verified before the first write, so a bad archive installs nothing. A directory whose files already verify is reported as skipped without a request, the executable path returned after a fresh install passes the supervisor's own validator, and the installer never executes the binary. Bundling the installed files and the catalog into the packaged application, signing the manifest, placing the generated notice in the packaged application and the Microsoft VC++ runtime remain M3/M12 work.
- First-run setup now installs its own pinned local runtime. The setup wizard accepts the validated sidecar manifest, adopts an already installed runtime from an offline check on refresh, and, when **Start local runtime** is used, calls `installSidecar`, reports bounded progress, validates the executable with the supervisor's own path check and only then returns the pinned start plan; a missing sidecar keeps `runtime-not-bundled`, while a failed, aborted or hostile install returns `runtime-install-failed` with a bounded code and can be retried, and the install never runs the binary. The docs check now rejects an unmerged conflict marker in any `docs/vibe` Markdown file, repairing the two that the #78 merge left in `ROADMAP.md` and `CHANGELOG.md` without failing a check.
- First-run setup now hands the local supervisor a validated, bounded restart policy instead of leaving it to the caller. The wizard accepts an optional `restart` policy (or uses the conservative default of three attempts, 1 s to 30 s exponential back-off and a 60 s stability reset), validates it with the supervisor's own exported validator, shows it in the setup panel, and exposes `runtimeOptions()` with exactly the `createLlamaServer` fields, so the pinned start plan can be passed to the supervisor without rebuilding flags. The wizard still never spawns a process, a selected daemon yields its own start plan, and the llama.cpp binary bundle and the packaged catalog copy remain M3 work.
- The local runtime can now discover an existing local Ollama daemon without typing a URL or a model name. `src/stable/runtime/ollama.mjs` makes at most one `GET /api/tags` request to the loopback host at a validated port (11434 by default), with a deadline, a 256 KiB response cap (raiseable to 4 MiB) and no credentials, evaluates the endpoint through the M1 policy before the request (a denial returns `policy-denied` with no request), and projects the answer through own data descriptors: a name-sorted, bounded model list that treats null metadata as absent, marks embedding and cloud/remote models, picks the largest local chat model and the largest local embedding model, and returns bounded notices instead of throwing or echoing the body. `toOllamaProviderOptions` returns exactly the `baseUrl` and `model` overrides the B1 `ollama` preset takes and refuses an unavailable result, an unknown, remote or embedding-only model, or a forged or stale default. The acceptance test drives the preset through the discovered base URL for chat, streaming, tool calls and embeddings against a loopback mock server. The first-run wizard now calls it (see the first-run detection bullet below); wiring it into the provider setup panel, a live smoke, the llama.cpp binary bundle, copying the catalog into the packaged application remain.
- First-run setup now notices an already running local Ollama daemon. The setup panel checks once when it opens and from a **Check for Ollama** button, then shows the loopback base URL, the local chat and embedding models and a note that the daemon is reported for provider setup (a later entry in this release adds explicit selection from the wizard). The wizard's `checkOllama()` is read-only and single-flight: it never changes the pinned plan, downloads nothing and never adopts the daemon on its own. It exposes the B1 `ollama` overrides only after the discovery result is re-validated, so a forged, stale, remote or wrong-base answer yields none, and a thrown or malformed answer becomes a bounded "not found" state instead of an error. Activating the daemon from the provider setup panel remains M2 work.
- The local daemon detected by first-run setup can now be selected as the local runtime. `useOllama()` validates that the stored summary still carries provider overrides, makes the wizard `ready` even when the pinned plan is `insufficient`, and switches the start plan to `kind: 'ollama'` with the validated loopback `baseUrl`, chat model and optional embedding model; `install()` then returns `ollama-selected` without downloading, `usePinned()` restores the pinned phase, and a re-check that loses the daemon releases the selection. The setup panel gains **Use Ollama** and **Use pinned models** controls with escaped values and precise statuses; it still never starts, installs or updates the daemon. A live-daemon smoke, the llama.cpp binary bundle, the packaged catalog copy and offering the daemon in the M2 provider panel remain later work.
- The local runtime supervisor can now recover a `llama-server` that dies while serving. An opt-in `restart` policy (`maxRestarts` 1-10, `baseDelayMs`, `maxDelayMs` and `stableMs`, all validated) restarts the child on the same loopback port with exponential back-off, waits for `/health` again, and reports `restarts` in the status; a run that stays healthy for `stableMs` earns the budget back, while a server that keeps failing ends in a bounded `failed` state with `failure: 'restarts-exhausted'` and no port instead of a crash loop. A stop during the back-off cancels the pending restart, a crash during an explicit start still fails closed as `server-exited`, and an omitted policy keeps the earlier `exited` behaviour. `src/stable/runtime/llama-server.mjs` and its fixture cover the policy, delays and bounds; bundling the llama.cpp binary and copying the catalog into the packaged application remain M3 work.
- The gateway now provides a dependency-free Router adapter that can ask the direct provider's Router for a prompt's difficulty. `src/stable/gateway/morph-router.mjs` sends exactly one bounded `POST /v1/router/classify` request and maps `easy`, `medium` and `hard` to the `cheap`, `standard` and `powerful` tiers, while a below-threshold or `needs_info` answer uses the configured default tier. When the Router is unavailable (timeout, network error, HTTP failure, malformed or oversized answer) it returns the default tier with a fixed code instead of failing the chat turn; caller cancellation, invalid input, a missing key and an M1 endpoint-policy denial still fail closed. The API key is read once and never returned, serialized or logged, the request refuses redirects and is bounded by a deadline and a response cap, and the answer is validated field by field. Mapping a tier to a provider and model in the B3 policy, and a live smoke test, remain M2 work.
- The first-run setup now composes hardware detection, the pinned catalog and the downloader into one flow. `src/stable/runtime/first-run.mjs` projects the catalog's chat and embedding entries to the four fields the recommendation accepts, probes the machine once, reports which pinned files are already installed, and refuses an insufficient machine rather than downloading weights that cannot run. It downloads only the missing files chat first, forwards progress, verifies each file before marking it installed, keeps a resumable partial after an abort or a failed transfer, and a retry skips models that already verified. The pinned start plan reports `runtime-not-bundled` until a binary is supplied or the start action installs the configured pinned sidecar, and otherwise carries the chat and embedding model paths plus the context, thread and GPU-layer numbers the supervisor consumes. The setup panel (`vibecodium.firstRun.open`) renders the verdict, steps, models, notices and progress and drives the check, download and start actions through bounded, escaped messages. The panel and wizard are not yet connected by the workbench. The llama.cpp binary bundle and copying the catalog into the packaged application remain M3 work.
- First-run hardware detection now reports what the machine can run before anything is downloaded. `probeHardware` collects platform, architecture, CPU model, logical core count, total and free memory and, on Windows, the display adapters from one fixed read-only PowerShell `Win32_VideoController` query whose child is the absolute system `powershell.exe`, bounded by a timeout and an output cap. Each adapter is returned with its decoded name, vendor, kind and reported memory (the script sends the name base64-encoded); a malformed, oversized, hostile or failed answer degrades to no GPUs with a bounded notice and never surfaces child output, and other platforms report that the GPU probe is unavailable instead of shelling out. `recommendRuntime` maps the facts and the pinned catalog to a frozen start plan: verdict, acceleration, chat and embedding model ids, context size, thread count, GPU layers, estimated chat and embedding memory and notice codes. A discrete GPU that can hold the smallest chat model (a 4 GiB card is enough for the pinned 1.5B chat model) offloads every layer, the WMI 4095 MiB `AdapterRAM` cap is marked `vram-capped` rather than mistaken for a small card, Apple silicon uses unified memory, an integrated or software GPU and a machine without a GPU stay on the CPU, RAM below 8 GiB is `insufficient` and below 16 GiB (or any CPU-only plan) is `tight`, and a GPU that cannot hold the smallest chat model falls back to RAM. The llama.cpp binary bundle remains M3 work; the local runtime restart/back-off policy has since been delivered in the supervisor module.
- The gateway now provides a bounded `codebase_search` tool that answers a natural-language question about the workspace through the WarpGrep model. A short read-only loop of at most six turns lets the model search literal text and read files, then finish with the answering paths and line ranges; the tool returns those spans with bounded content and token usage. It never writes, stays inside the caller's workspace, skips `.git`, dependency and build folders and credential-shaped files such as `.env` or `*.pem` by default, lists the workspace with relative paths only, refuses escaping, symlinked, binary and oversized files, caps every turn, tool call and result, and reports no query, file body, endpoint or credential in an error. The agent-host wiring remains M6 work; a live provider smoke test remains M2 work.
- Local model provisioning now has a pinned catalog and a resumable downloader. `vibe/models/catalog.json` pins two Apache-2.0 GGUF files (Qwen2.5-Coder 1.5B Instruct `q4_k_m` and Qwen3-Embedding 0.6B `q8_0`) by commit revision, SHA-256 and exact byte size, and the catalog refuses a branch revision, a non-GGUF or nested file name, a disallowed license, a plain-http non-loopback URL and a URL with credentials, query or fragment. `downloadModel` streams the weights into a partial file, resumes an interrupted transfer with a `Range` request, follows a redirect only to another HTTPS URL, or loopback HTTP when the pinned URL is loopback, keeps a partial file after a cancellation, stall, timeout or dropped body, checks free space before the first request, and installs a file only when its size and digest match the pin; a mismatch removes the partial file and never leaves unverified bytes under the final name. `verifyInstalledModel` reports whether a model is already installed without touching the network. The `llama-server` binary and copying the catalog into the packaged application remain M3 work.
- The local runtime now has a supervisor for a caller-supplied llama.cpp `llama-server`. It starts a direct child with `shell: false` on `[127.0.0.1]`, passes the server flags exactly `--model`, `--host` and `--port` plus optional bounded context, thread and GPU-layer flags, resolves `start()` only after `/health` returns 200 and reports the port, base URL and pid. `stop()` is idempotent and escalates from `SIGTERM` to `SIGKILL`; never-ready and unhealthy children are stopped, and an early-exit child fails closed as `server-exited`. The executable and model must be real files with no symlink or junction in the path, the child runs in the executable directory with an allowlisted environment and an empty `PATH` unless the caller supplies one, loader/system and `LLAMA_ARG_*` environment names are refused case-insensitively, prefix arguments cannot enable a shared port or the agent/MCP tools, and the controller, its argument list and its status are frozen. The B1 `llama-cpp` preset serves chat, streaming, tool calls and embeddings from the fixture spawned by the supervisor in the acceptance test; connecting the preset to a supervised server in the product remains later M3/M6 work. Bundling the llama.cpp binary remains M3 work; the pin and verified installer are delivered in the entry above.
- The gateway now provides a bounded `edit_file` tool that merges a lazy edit into an existing workspace file through Fast Apply. The tool sends one `<instruction>`, `<code>` and `<update>` turn to `morph-v3-fast` through the provider client, then writes the merged result atomically. It stays inside the caller's workspace, refuses absolute, traversal, UNC, encoded, symlink, missing, binary and oversized targets, re-checks the original immediately before the rename (a narrow check-to-rename race remains), and reports no source, prompt, credential or response body. The agent-host wiring remains M6 work.
- The context engine now has a standalone history compactor that reduces a chat history to a token budget without rewriting it; the in-IDE history path is not yet surfaced. `src/stable/context-engine/compact.mjs` keeps every `system` message, explicitly pinned messages and the newest messages, drops whole older messages and only the oldest whole lines of one boundary message, and guarantees that every surviving line is byte-identical to its source; pinned content that alone exceeds the budget fails closed instead of silently truncating, and histories that carry tool calls are rejected until tool-call pairing can be dropped as a whole. A caller tokenizer is supported but must match or exceed the D4 byte estimate and be monotone, and the reported estimate never exceeds the budget. Oversized histories, under-counting tokenizers and a tokenizer that fails a monotonicity probe fail closed; message, character and line caps bound the input as it is read and split.
- Model work now has a deterministic direct second option. A dependency-free helper builds the full six-class B3 policy with OmniRoute first and the direct provider second, using an explicit model and output cap for each class in place of silent defaults. With OmniRoute stopped, chat and embeddings still complete on the direct provider in the same turn; the answer reports the serving provider and bounded attempt metadata that contains no response body, prompt, endpoint or credential. A missing, extra, malformed, accessor-backed or reserved-key map fails closed without invoking a getter or echoing a value. WarpGrep, Router, hosted models, the approval-gated abliterated model and live smoke tests remain B6 work; Fast Apply agent-host wiring remains M6.
- Model providers can now be added and switched from a provider setup panel without editing a file. The panel lists the catalog, marks the active provider, shows whether a key is stored, offers environment-variable names (each preset configured key variable plus credential-shaped names set in the process) as the key picker (never their values), and imports the selected variable's value into the Windows Credential Manager. Provider definitions are stored in a non-secret settings file that records only which providers have a stored key; a definition containing a secret field is rejected, and no key is ever rendered in the panel, returned by the setup API, written to a file or included in an error. The real Credential Manager round-trip is environment-limited in the agent sandbox, where a restricted token returns ERROR_NO_SUCH_LOGON_SESSION; the adapter protocol, failure mapping and PowerShell script parse are covered by tests. Bifrost supervision, the B6 direct-provider features and live provider smoke tests remain M2 work.
- Model work can now be routed by task class. A validated policy table selects the provider, model and output cap for plan, code-edit, quick-edit, review, summarize and embed, composes the ordered provider fallback for each class, reports the selected and serving provider, and sends the chat output cap on both OpenAI Chat and OpenAI Responses requests. Per-task and UTC-day token budgets reserve an exact JSON-serialized input bound plus the cap before dispatch and stop a request with a bounded `budget-exhausted` error, without calling a provider, when either budget cannot cover it; request data is snapshotted, the task map fails closed at its cap, and used tokens cannot be reset by the caller. Provider response bodies, prompts, credentials and client objects never enter the budget or routing metadata.
- Provider requests can now use an ordered fallback chain. A timeout, network error, HTTP 408/429/5xx or empty answer moves to the next configured provider in the same turn, including streaming text and tool calls, while policy denials, authentication problems, invalid requests and cancellation still stop immediately. Successful answers report which provider served them, and an exhausted chain fails with bounded attempt summaries that contain no response body, prompt or credential. Bifrost wiring remains future M2 work.
- The M2 B1 provider layer now ships a dependency-free, frozen catalog for OmniRoute, Morph, kie.ai Responses, DeepInfra, Abliteration, OpenRouter, Requesty, any OpenAI-compatible endpoint, llama.cpp and Ollama, plus a settings-JSON path that can add a provider or override a built-in without editing source. A request client implements both OpenAI Chat Completions and OpenAI Responses, assembles streaming text and streamed tool arguments under event/byte caps, exposes embeddings only where a preset advertises them, reads the credential once and never returns, serializes or logs it, suppresses provider response bodies from HTTP errors, and sends every request through the M1 deny-by-default endpoint policy; local model servers stay allowed by default, while a remote preset needs an exact host/endpoint allow or the external-provider opt-in, which the client scopes to the configured host. Every request refuses redirects, keeps the deadline armed until the body is consumed, requires an async-iterable body under the byte cap, and rejects control or bidi characters in a credential; the external-provider opt-in applies only to endpoints the policy classifies as external-provider or unknown, so it cannot reach Copilot, Copilot-telemetry, GitHub or metadata hosts. Bifrost supervision and live smoke tests remain M2/M3 work.
- The M1 Microsoft endpoint audit now ships as `docs/vibe/design/m1-endpoint-audit.md` plus a dependency-free, deny-by-default decision core in `src/stable/security/ai-endpoint-policy.mjs`. The audit covers the Microsoft, GitHub Copilot CAPI, Copilot telemetry, 1DS telemetry, Azure ML model-catalog and upstream VS Code update hosts reachable from the pinned `1.143.1` AI services in the scanned directories, with the source file and disposition for each. `evaluateAIEndpointRequest()` allows loopback, private-LAN and on-device model servers by default and denies every remote family until a caller opts in by category, exact host or host+path; credential URLs, non-HTTP schemes, control/bidi characters, punycode hosts and invalid options fail closed; option bags with accessors are rejected without invoking them, string arrays are read only through own data descriptors so accessor indices and custom iterators never run, proxy traps can run during structural inspection while any trap failure or revoked proxy fails closed as `invalid-options`, array holes also fail closed, and prototype pollution cannot supply a switch value in decisions or policy summaries; `redactAIEndpoint()` keeps logs free of userinfo, query and fragment. IPv4/IPv6 link-local ranges and the enumerated cloud-metadata hostnames and addresses are hard-denied before any opt-in is considered; mDNS `.local`/`.localhost` aliases are re-checked against the same hard-deny set, the whole local-use NAT64 range and the IPv4 metadata addresses embedded in the well-known NAT64 range are hard-denied, and IPv6 unique-local addresses need an exact host or host+path allow. Live interception stays M2 (Bifrost) and M6 (agent host) work.
- The native VS Code AI surfaces now open on a clean profile without a user-installed GitHub Copilot extension or a GitHub sign-in. `prepare_vscode.sh` applies a dependency-free product transform after merging `product.json`: it replaces `defaultChatAgent` with a Vibecodium descriptor owned by the built-in `vibecodium.vibecodium-ai` extension, removes every Copilot-branded entry from the owned sections (default chat agent, trusted auth, built-in/auto-update, recommendation including language, tool and chat-session tips, session, API-proposal, gallery-property, forced-version, auth-inheritance, remote-default-extensions and configuration-policy lists) and leaves only the gallery telemetry SKU names and the workspace-trust copy alone; the build also drops the bundled `extensions/copilot` folder, and points every runtime endpoint at the reserved `https://vibecodium.invalid` host. The built-in extension defaults `chat.disableAIFeatures`, `chat.titleBar.signIn.enabled` and `chat.welcomePage.signIn.enabled` so chat stays on and sign-in prompts stay off, including on hosts that predate the welcome-page setting.
